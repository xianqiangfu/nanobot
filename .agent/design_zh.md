# 设计约束

这些规则指导架构决策。在添加功能或修复错误时，应选择遵守这些边界的路径。

## 核心保持精简；在边缘扩展

新能力应通过 `channels/`、`tools/`、技能或 MCP 服务器添加。`agent/loop.py` 和 `agent/runner.py` 文件构成关键核心路径；对其中的更改应最小且必须有充分理由。如果一个功能可以在通道适配器、工具或外部 MCP 服务器中实现，则不应内联到代理循环中。

## 少结构，多智能

优先选择简单、可读的代码，而非新的框架层和间接引用。只有当结构能够消除真正的复杂性、保护重要边界或匹配既定的本地模式时才添加结构。最佳修复通常是一个更小的提示、更紧密的工具契约、通道本地更改或一个专注的回归测试。

## 优先选择重复而非过早抽象

通道和提供者允许重复类似的逻辑（发送重试、媒体处理、消息拆分）。不要为了消除通道文件间的重复而引入复杂的基类或共享助手。每个通道文件应保持独立且可读。同样适用于提供者实现。

## 解决实际问题所需的最小更改

通过仅更改必要的部分来修复错误。不要将不相关的重构或清理打包到功能或错误修复 PR 中。如果确实需要重构，则应将其作为针对 `nightly` 分支的单独 PR。

## 保持 PR 可审阅

错误修复应明确保护的不变式，更改执行该不变式的最小范围，并仅添加最接近的回归测试。如果差异开始更改所有权边界或将行为更改与清理混合，应在它变得难以审阅之前进行拆分。

## 显式而非魔法

配置必须在 `config/schema.py` Pydantic 模型中显式声明。错误处理应引发明确的异常，而非静默修正不良输入。虽然存在提供者自动检测功能，但每个解析路径必须可从工厂追踪到具体的提供者类。
